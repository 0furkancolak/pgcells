# Supported tenant SQL

Application queries live in `src/queries/<tenant|node|platform>/<area>.sql` (the folder is the scope: tenant schemas, or the `platform` schema of every database / of db0) as `-- name: <camelCaseName>` blocks (names are unique across the package); `bun run codegen` compiles each file's blocks with this grammar into its own committed module (`src/queries/tenant/auth.sql` → `src/queries/tenant/auth.gen.ts`, imported as `@0furkancolak/pgcells/queries/tenant/auth`), and `bun run codegen --check` (CI) rejects stale, orphan or hand-edited output. The runtime entry (`src/index.ts`) never loads the parser. CLI code and tests can compile at runtime with `prepareQuery(source)`. Execute the resulting `PreparedQuery` through the tenant query API with a separate parameter array. `prepareMigration(source)` is the separate DDL preparation entrypoint. Both reject unsupported SQL with `AppError.code === "SQL_UNSUPPORTED"` before dispatch. These definitions are application code, not an interface for accepting SQL from clients.

```ts
const users = prepareQuery(
  "SELECT id::text AS id, name FROM users ORDER BY users.id LIMIT $1 OFFSET $2",
);
// users.bind(validTenantSchema) returns SQL; values remain $1 and $2.
```

Preparation parses the source once with pinned `pgsql-ast-parser@12.0.2`, checks explicit static AST field rules in `src/core/sql/grammar.ts` and semantic checks in `src/core/sql/compiler.ts`, and compiles immutable string parts from source positions. Binding validates the tenant schema format (`tenant_` or `demo_` followed by `[a-z0-9_]`, at most 63 bytes, derived from the tenant domain) and joins those parts. There is no tenant cache, AST traversal during binding, marker replacement, or session setting. Table spelling, aliases, parameters, ordinary quoted strings, comments, and non-target SQL text remain intact. Builtin types and ordinary builtin functions are emitted with explicit `pg_catalog` qualification, except bare `INTERVAL` syntax as described below. PostgreSQL may still reject a supported statement for normal semantic reasons such as missing columns or invalid argument types; the compiler does not replace database validation.

## Comments, quoting and execution errors

Before AST parsing, line comments and nested block comments are masked with equal-length whitespace while preserving newlines and source offsets. Quotes inside comments have no syntactic effect; comment delimiters inside quoted strings or identifiers remain data. Binding uses the original source, preserving comments and bound-value separation. A second statement hidden behind a misleading comment still rejects.

Connections must use PostgreSQL `standard_conforming_strings=on` (the default). Ordinary strings use doubled quotes; only `E'…'` escape strings treat backslashes as escapes. Dollar-quoted values and Unicode-escaped `U&'…'` / `U&"…"` quoting reject, as do unterminated comments or quoted tokens. The compiler does not change session settings to support other quoting modes.

Tenant queries use autocommit unless enclosed in `tenant.transaction`. A caught autocommit query error can be followed by another query in the same live context; an uncaught query failure still propagates. A statement failure inside an explicit transaction poisons that transaction even when caught, so the transaction rolls back. Closing a context prevents new work and drains started queries before its transaction closes.

## Runtime statements

Exactly one nonempty statement is accepted, optionally terminated by a semicolon:

- `SELECT`, including table/view references, table and projection aliases, inner/outer/cross joins, `ON`/`USING`, subqueries (including correlated subqueries), `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`, `LIMIT`, `OFFSET`, `DISTINCT`, and `DISTINCT ON`.
- `VALUES`, `UNION`, and `UNION ALL`.
- Nonrecursive `WITH`, including nested shadowing, previous CTE references, and data-modifying CTEs. A binding does not see itself; it can see earlier bindings and enclosing CTEs. DML targets always denote tenant relations even if a CTE has the same name.
- `INSERT ... VALUES` or `INSERT ... SELECT`, with column lists, `RETURNING`, and `ON CONFLICT` as described below.
- `UPDATE ... SET`, optional `FROM`, `WHERE`, and `RETURNING`.
- `DELETE`, optional `WHERE` and `RETURNING`.

### Output column names

TypeScript result keys are camelCase while columns stay snake_case. The mapping is compiled into the SQL text: PostgreSQL returns camelCase column names, so there is no per-row key renaming, no driver transform and no runtime cost. `src/core/sql/casing.ts` inserts or replaces source spans after validation, like schema qualification; binding is unchanged. Migrations and seeds are not renamed.

Only the outermost output list is renamed: the top-level `SELECT` projection (the final statement after `WITH`; for `UNION`/`UNION ALL` the first branch, whose names PostgreSQL uses) or the `RETURNING` list of a top-level `INSERT`/`UPDATE`/`DELETE`. CTE bodies, subqueries (in `FROM` or in the projection), `INSERT ... SELECT` projections (positional), `ON CONFLICT` and `excluded.column` stay untouched; outer SQL keeps referring to them by their SQL names. `camelCase` removes an underscore between two lowercase letters/digits (`first_name` → `firstName`); other names are unchanged. Parameters are positional and need no mapping.

- An unaliased column reference, qualified or not, optionally wrapped in parentheses or casts (PostgreSQL names those after the column), gets an alias when its name changes: `s.first_name` → `s.first_name AS "firstName"`, `created_at::text` → `created_at::"pg_catalog"."text" AS "createdAt"`.
- An unquoted alias is folded to lowercase like PostgreSQL does, then camelized and quoted: `AS full_name` → `AS "fullName"`, `last_name family_name` → `last_name "familyName"`. `AS fullName` is `fullname` in PostgreSQL and stays `fullname`.
- A quoted alias is kept verbatim. This is the escape hatch for an exact name: `AS "full_name"`.
- Other unaliased expressions keep PostgreSQL's default name (`count(*)` → `count`, `date_trunc(...)` → `date_trunc`); alias them to choose a name.
- `*` and `t.*` expand at compile time to a qualified column list (`"s"."first_name" AS "firstName", ...`) exactly when at least one of their columns changes name; otherwise the star stays as written. Columns come from the migration table registry of the query's scope (the same folded migrations that generate `src/tables/`), from a CTE or `FROM` subquery whose own projection names are known (explicit aliases, column references, calls, stars over known sources; a `sub(a, b)` column list renames the leading columns), or from the DML target (plus `UPDATE ... FROM` items for `RETURNING *`). A star whose columns are unknown, an unqualified star over a `USING` join, or a star over a relation missing from the registry rejects with `SQL_UNSUPPORTED`; list the columns explicitly.
- Duplicate output names after renaming (for example `first_name` and `"firstName"`, or `s.id` and `c.id`) reject, because row objects would silently drop one of them.
- `ORDER BY` and `DISTINCT ON` resolve a bare name to an output column first, so a bare reference to a renamed output is rewritten to its new quoted name. The `ORDER BY` the parser attaches to a union's last unparenthesized branch belongs to the union and is rewritten the same way. `GROUP BY` resolves a bare name to an input column first; a bare `GROUP BY` reference to a renamed explicit alias rejects (group by the expression or position, or quote the alias).

`bun run codegen` passes each scope's folded migration tables. `prepareQuery(source, scope, tables)` compiles identically when given the same `tables`; without `tables` it knows no relation columns, so a renaming-relevant `*` over a real table rejects while everything else behaves the same. The `@0furkancolak/pgcells/management` `prepareQuery(source, scope)` supplies the package's own migration registry for the scope, so the CLI, tests and tools match codegen.

```ts
prepareQuery("SELECT u.email_verified, created_at AS created_on FROM users u ORDER BY created_on", "tenant", tables);
// SELECT u.email_verified AS "emailVerified", created_at AS "createdOn" FROM "<schema>".users u ORDER BY "createdOn"
```

### Upserts, windows and row locks

`ON CONFLICT DO NOTHING`, column/expression targets, and `ON CONSTRAINT name` are supported. `DO UPDATE SET` supports the same reviewed expressions as ordinary updates, including correlated subqueries and an action `WHERE`. `excluded.column` and target aliases retain PostgreSQL reference semantics; they are not relation targets. A real `FROM excluded` still receives the tenant schema unless it resolves to a CTE. Constraint names remain local to the insert target; explicitly schema-qualified constraints reject. Partial-index inference predicates (`ON CONFLICT (...) WHERE ...`) are not represented by the pinned parser and reject.

```ts
const upsert = prepareQuery(
  "INSERT INTO users(name,email) VALUES ($1,$2) ON CONFLICT (email) DO UPDATE SET name=excluded.name RETURNING id",
);
await tenant.query(upsert, [name, email]);
```

`OVER ()`, `OVER (PARTITION BY ...)`, `OVER (ORDER BY ...)`, and their combination are accepted for approved calls, including existing aggregates and `row_number`, `rank`, `dense_rank`, `percent_rank`, `cume_dist`, `ntile`, `lag`, `lead`, `first_value`, `last_value`, and `nth_value`. Partition and ordering expressions receive the same recursive validation and relation qualification as ordinary expressions. The compiler preserves PostgreSQL's default frame; it never inserts or rewrites a frame. Explicit `ROWS`/`RANGE`/`GROUPS` frames are supported in the strict form described under Parser gaps; named windows reject. PostgreSQL remains responsible for checking whether a particular call can be used as a window function.

`FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, and `FOR KEY SHARE` accept optional `NOWAIT` or `SKIP LOCKED`. Any lock clause, including one nested in a subquery or CTE, sets the immutable prepared query's `requiresTransaction` flag. The tenant context rejects it with `TRANSACTION_REQUIRED` before SQL dispatch unless it is executed through `tenant.transaction`; manually constructed or copied prepared objects cannot bypass the existing identity check. Parser-unsupported `OF` relation lists reject. A wait policy without a lock clause also rejects.

```ts
await tenant.transaction(tx => tx.query(
  prepareQuery("SELECT id FROM users FOR UPDATE SKIP LOCKED"),
));
```

Every actual relation reference and DML target receives the bound tenant schema. CTE references and aliases do not. Explicit relation schemas, including `public`, other tenants, and `pg_catalog`, reject (the only exception is the `pull` source-schema rewrite described under migration statements, which removes them before compilation). Schema-qualified column references reject. Identifiers must fit PostgreSQL's 63-byte UTF-8 identifier limit so truncation cannot change CTE resolution. The compiler cannot identify catalog object kinds from syntax: preexisting tenant views must be trusted migration-owned views, and it does not inspect their definitions.

Supported expressions are column/star references, positional `$n` parameters, ordinary scalar literals, `NULL`, `DEFAULT`, builtin casts/typed literals, lists, arrays, array subscripts/subqueries, `CASE`, `BETWEEN`/`NOT BETWEEN`, and the approved calls/operators below. `EXTRACT(field FROM expr)` is accepted: PostgreSQL always resolves it to `pg_catalog.extract`, and the field is a keyword. Aggregates support `DISTINCT`, inner ordering, `FILTER`, and `WITHIN GROUP`. Time value keywords are `CURRENT_DATE`, `CURRENT_TIME`, `CURRENT_TIMESTAMP`, `LOCALTIME`, and `LOCALTIMESTAMP`.

Approved ordinary calls (unqualified or explicitly `pg_catalog`, always rendered explicitly qualified): `count`, `sum`, `avg`, `min`, `max`, `lower`, `upper`, `length`, `char_length`, `abs`, `round`, `ceil`, `floor`, `now`, `date_trunc`, `date_part`, `to_char`, `gen_random_uuid`, `split_part`, `json_agg`, `jsonb_agg`, `json_build_object`, `jsonb_build_object`, `array_agg`, `string_agg`, `unnest`, `generate_series`, `jsonb_set`, `jsonb_each`, `jsonb_each_text`, `jsonb_array_elements`, `jsonb_array_elements_text`, `jsonb_extract_path`, `jsonb_extract_path_text`, `concat`, `replace`, `btrim`, `ltrim`, `rtrim`, `regexp_replace`, `regexp_match`, `regexp_matches`, `array_length`, `to_tsvector`, `to_tsquery`, `plainto_tsquery`, `websearch_to_tsquery`, `ts_rank`, plus `trim(x)` (rendered as `pg_catalog.btrim`), and the window calls listed above.

SQL syntax calls `any`, `coalesce`, `nullif`, `greatest`, `least`, and `exists` must be unquoted and unqualified; quoted lookalikes reject. `ANY (ARRAY[...])` also accepts PostgreSQL's catalog-normalized form of an `IN (...)` CHECK constraint.

Approved binary operators: `OR`, `AND`, `IN`, `NOT IN`, `LIKE`, `NOT LIKE`, `ILIKE`, `NOT ILIKE`, `=`, `!=` (including the parser's normalization of `<>`), `>`, `>=`, `<`, `<=`, `+`, `-`, `*`, `/`, `%`, `||`, `@>`, `<@`, `?`, `?|`, `?&`, `#>>`, `~`, `~*`, `!~`, `!~*`, `@@`, `&&`, `<<`, `>>` (`-|-`, `<<=` and `>>=` are not parseable by the pinned parser and reject), and the `member` forms `->`/`->>` (literal key only; the parser cannot parse `#>`). Approved unary operators: `+`, `-`, `NOT`, `IS NULL`, `IS NOT NULL`, `IS TRUE`, `IS FALSE`, `IS NOT TRUE`, `IS NOT FALSE`. Explicit `OPERATOR(schema.op)` and all other operators reject. These operators use PostgreSQL's normal builtin resolution on migration-owned builtin column types; tenant SQL cannot configure session resolution or install custom operators/types.

Approved types and ordinary SQL aliases: `uuid`, `text`, `boolean`/`bool`, `smallint`/`int2`, `integer`/`int`/`int4`, `bigint`/`int8`, `real`/`float4`, `double precision`/`float8`, `numeric`/`decimal`, `varchar`, `bpchar`, `bytea`, `json`, `jsonb`, `date`, `time`, `timetz`, `timestamp`, `timestamptz`, `interval`, `inet`, `cidr`, `macaddr`, `tsvector`, `tsquery`, `int4range`, `int8range`, `numrange`, `tsrange`, `tstzrange` and `daterange`. The last eleven are scalar-only: arrays of them reject (drivers disagree on array values). `serial`/`smallserial`/`bigserial` are accepted only as a column type in `CREATE TABLE`/`ADD COLUMN`, written bare (never qualified) and folded to `int4`/`int2`/`int8` with `NOT NULL` and a default; anywhere else they reject. `citext` and other extension types reject (their schema is provider-specific and there is no `search_path`). Unmodified arrays and parser-supported scalar numeric type modifiers are accepted. Array element modifiers (for example `varchar(10)[]`) reject because the pinned parser omits modifiers from their source spans. Long `WITH/WITHOUT TIME ZONE` aliases and `character varying` reject because their source spans are incomplete (and `time(3) WITH TIME ZONE` is mislabeled as timestamp). Use `time`, `timetz`, `timestamp`, `timestamptz`, or `varchar` explicitly. `char` and `character` aliases reject rather than losing their implicit length-one semantics; use `bpchar(1)` for that behavior. Types normalize to canonical qualified catalog names. Bare unquoted, unqualified `INTERVAL` retains its original PostgreSQL syntax, including precision and literal field qualifiers: `interval(3)`, `CAST($1 AS INTERVAL(3))` and `INTERVAL '1 year 2 months' YEAR` remain intact. PostgreSQL already treats this syntax as its builtin system type; qualifying it would alter typmod/field semantics. Quoted `"interval"` and explicitly qualified `pg_catalog.interval` follow ordinary catalog-name qualification. Quoted aliases that differ from the actual catalog type name reject rather than silently changing quoted-name semantics.

## Migration statements

The same grammar covers tenant migrations and the platform/node `platform` migrations run by `bootstrap`; `bind(schema)` accepts a valid tenant schema or exactly `platform`. Migration files are `--up`/`--down` sections (see the package README); each section is prepared separately with `prepareMigration(source, types)`, and the prepared object also exposes the parsed `statements` (the registry derives concurrent-index handling and codegen derives table types from them). A nonempty source may contain multiple supported DDL statements. `bind(schema)` returns a frozen array of complete statements in source order, retaining semicolons and inter-statement comments. Transaction policy remains the migration runner's responsibility.

- `CREATE TABLE [IF NOT EXISTS]` with explicit columns, approved builtin types, `NULL`/`NOT NULL`, defaults, primary keys, unique constraints (including `UNIQUE NULLS NOT DISTINCT`), checks, identity columns, and column/table foreign keys (including parser-supported referential actions). Table and FK targets are qualified.
- Identity columns: `GENERATED ALWAYS|BY DEFAULT AS IDENTITY [ ( sequence options ) ]` with `SEQUENCE NAME`, `AS <builtin type>`, `INCREMENT BY`, `MINVALUE`, `MAXVALUE`, `START WITH`, `CACHE` and `[NO] CYCLE`. PostgreSQL creates an unqualified sequence name in the table's schema; the compiler still writes it qualified with the bound schema (`sequence name "<schema>"."t_id_seq"`), so no sequence name depends on session state. A schema-qualified sequence name, `OWNED BY`, and stored generated columns (`GENERATED ALWAYS AS (expr) STORED`) reject. `serial`, `CREATE SEQUENCE` and `nextval('…')` reject because the sequence name would be schema-bearing text. Keywords are case-insensitive and quoted identifiers keep their spelling, so Better Auth's generated DDL (`create table "user" ("emailVerified" boolean not null, "createdAt" timestamptz default CURRENT_TIMESTAMP not null, "userId" text not null references "user" ("id") on delete cascade)`) compiles unchanged; `ON DELETE CASCADE` stays inside the tenant because the referenced table is qualified.
- `ALTER TABLE [IF EXISTS]`: add/drop columns (including parser-supported existence guards), rename columns/table/constraints, set/drop defaults, set/drop `NOT NULL`, change a column to an approved builtin type or migration-created enum, `ALTER COLUMN … ADD GENERATED … AS IDENTITY`, and add/drop the supported constraints. `SET`/`DROP IDENTITY` are not parsed and reject. Defaults and check expressions use the same reviewed expression grammar. Foreign-key targets are qualified. Multiple alterations are accepted. `DROP COLUMN` and `DROP CONSTRAINT` allow default/`RESTRICT` behavior; `CASCADE` rejects.
- Type changes accept `[SET DATA] TYPE t USING expr`. The expression is compiled with the same reviewed expression grammar (casts to enums and builtin types are qualified). See the parser gaps below for how this clause is located.
- `CREATE [UNIQUE] INDEX [CONCURRENTLY] [IF NOT EXISTS]`, with an optional builtin access method (`USING btree|hash|gin|gist|brin`; access methods are not schema objects), ordinary expressions, order/null ordering, an unqualified per-expression `COLLATE "name"` (rendered as `"pg_catalog"."name"`), and optional `WHERE`. The indexed table is qualified. The index name stays local because PostgreSQL creates it in the indexed table's schema.
- `CREATE TYPE name AS ENUM (...)` and `DROP TYPE [IF EXISTS]` qualify the type name. Later references to such an enum in the same source or in later migrations of the same registry (column types, `ALTER COLUMN TYPE`, casts such as `'admin'::"role"`) render as `"<schema>"."name"`, never through `search_path`; the registry passes the enum set from file to file. Enum names may not shadow builtin type aliases; schema-qualified, unknown or modifier-bearing custom types still reject, and runtime queries never accept custom types. `ALTER TYPE name ADD VALUE [IF NOT EXISTS] 'v' [BEFORE|AFTER 'w']` qualifies the enum; other `ALTER TYPE` forms (rename, rename value, schema/owner changes) reject.
- `INSERT`, `UPDATE`, `DELETE` and nonrecursive `WITH` (data migrations; SQL seeds accept only the first three) follow exactly the runtime DML rules above, with every target qualified.

- `DROP TABLE [IF EXISTS]`, `DROP INDEX [CONCURRENTLY] [IF EXISTS]` and `DROP TYPE` qualify every name in the list and allow default/`RESTRICT` behavior. `DROP TABLE|TYPE … CASCADE` is accepted only when every dropped table/type was created by an earlier statement of the same migration section (renames are followed). A section runs in one transaction, so no object in another schema can depend on an object that is not yet committed. `CASCADE` on anything else, and on `DROP INDEX`, `DROP COLUMN` or `DROP CONSTRAINT`, rejects because dependencies may cross schema boundaries. The registry accepts `CONCURRENTLY` (create or drop) only as the single statement of a tenant section, which the runner executes outside a transaction with its own retry inspection.
- `ALTER INDEX [IF EXISTS] name RENAME TO new_name` qualifies the existing index, leaving the new name local to its schema. Qualified rename destinations, schema moves, and tablespace changes reject.

```ts
prepareMigration(
  "ALTER TABLE users ADD COLUMN phone text; ALTER TABLE users RENAME COLUMN phone TO contact_phone;",
).bind(schema);
```

### Parser gaps

`pgsql-ast-parser@12.0.2` cannot parse three clauses that PostgreSQL catalog output (`pull`) and hand-written migrations use: `USING expr` after `ALTER COLUMN … TYPE`, `NULLS NOT DISTINCT` after `UNIQUE`, and `IF NOT EXISTS` / `BEFORE|AFTER 'w'` in `ALTER TYPE … ADD VALUE`. In migrations and runtime queries, `src/core/sql/parser-gaps.ts` finds these clauses in the comment-masked source with quoted text hidden:
- `USING` must be at parenthesis depth 0 of an `ALTER TABLE` statement and runs to the next depth-0 comma or the statement end.
- `NULLS NOT DISTINCT` must directly follow `UNIQUE`.
- The enum clauses require the whole `ALTER TYPE` statement to match a strict pattern.

Each clause is replaced by equal-length whitespace only in the text given to the parser; source positions and the emitted SQL are unchanged. After parsing, each clause must attach to exactly the AST node that ends immediately before it (a `set type` change, a `unique` constraint whose `[CONSTRAINT name] UNIQUE` keyword precedes it, or an `add value` change). It is added as a field (`using` is parsed separately as an expression with shifted positions), and the grammar then walks that field with its normal rules. A clause that attaches to no node rejects, so it can never silently change the meaning of a different statement.

Runtime queries (and data migrations) also use the gap finder for constructs the parser cannot represent but whose meaning the walker never needs. These are replaced in the parser's copy only, by a word of at most the same length, at whole-keyword boundaries outside quotes and comments: `INTERSECT`/`EXCEPT` → `UNION`, `IS [NOT] DISTINCT FROM` → `<>`/`=`, `GROUPING SETS` → `ROLLUP`. A strict window frame (`ROWS|RANGE|GROUPS` with `UNBOUNDED`/`CURRENT ROW`/integer bounds, ending the `OVER (…)` parentheses) is blanked. The emitted SQL always comes from the original source, so PostgreSQL parses the real keyword; the walker only validates leaf `SELECT`s, scopes, functions and the first branch's output names, none of which depend on set-operation shape or operator precedence. `WITH RECURSIVE` blanks `RECURSIVE` and attaches `recursive` to the `with` node so every CTE alias is in scope inside every body. `ROLLUP`/`CUBE` are parsed as calls and accepted only as direct `GROUP BY` items (nested ones, empty grouping sets and the same names elsewhere reject); `grouping()` is a special call, never qualified.

### Source schemas (`pull`)

`unqualifyMigration(source, sourceSchemas, types, created)` walks the same grammar with a set of allowed source schemas (for `pull`: the pulled schema, whose `pg_get_*def` output qualifies names; `search_path` is never used). For relation, DML target, FK target, sequence name and type nodes whose schema is in that set, it removes the `schema.` prefix at its AST position. It returns the schema-free source, which is then compiled normally. Any other explicit schema rejects, and a stripped relation name that would now resolve to a CTE rejects. Aliases, column qualifiers and string literals that spell the schema name are not touched. `prepareMigration` itself never accepts an explicit schema.

Destructive DDL is exclusively developer-authored immutable migration code, never SQL supplied by an application client. Existing migration bytes, IDs and checksums must not be edited to adopt new grammar. Add a new migration and follow the existing runner's transaction/recovery policy. Default/`RESTRICT` behavior intentionally lets PostgreSQL refuse drops when neighboring objects depend on the target.

DDL is not accepted by the runtime API.

## Deferred grammar and trust boundary

Unknown AST node kinds and unknown fields reject; they are never passed through as an unchecked fallback. Unsupported constructs include named windows, lock `OF` lists, partial-index conflict inference predicates, insert overriding, extension or user-defined functions/operators, custom types other than migration-created enums, `ALTER TYPE` forms other than `ADD VALUE`, standalone sequences, `nextval`, stored generated columns, catalog relation access, relation-name casts such as `regclass`, collations outside index expressions (and qualified collations), custom index methods/opclasses/options/tablespaces, table inheritance/LIKE/temporary/unlogged forms, view creation, ALTER forms not listed above (including identity `SET`/`DROP`, row level security, ownership and schema changes), cascading drops outside the same-section rule, other DROP object kinds, `NULLS NOT DISTINCT` on indexes, `DELETE … USING`, COPY, schema/role/transaction/session commands, SQL PREPARE, function bodies, DO/PL/pgSQL, and dynamic SQL. Parser-unsupported syntax, including dollar-quoted value literals, also rejects. Functions in FROM are supported only with an alias (a column list enables `*`).

The parser and trusted application source are part of the boundary. The compiler does not authorize a tenant, restrict which table names application code may use within that tenant, examine existing database views/triggers/functions, or defend against an administrator replacing builtin catalog objects. Database ownership and tenant authorization remain separate controls. Extending this grammar requires reviewing the new AST fields, schema-bearing references, source locations, and rejection/transformation tests; upgrading the pinned parser requires the same review.
